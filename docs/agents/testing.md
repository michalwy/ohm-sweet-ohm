# Testing

## Which suite, when

A suite runs when it could see the change. A documentation-only change runs none. The report — and
the PR body — says which suites ran, which did not, and why.

| Command | Covers | Required when |
| --- | --- | --- |
| `pnpm lint` | ESLint over the repository, minus the ignores in `eslint.config.mjs` | any change to source files. Fix every error; warnings may stay. |
| `pnpm typecheck` | Prisma codegen, `next typegen`, `tsc --noEmit` | any change to TypeScript or the Prisma schema |
| `pnpm test:unit` | `tsx --test tests/unit/**/*.test.ts` — pure logic | changes to logic those tests reach |
| `pnpm test:integration` | server-side tests against a real PostgreSQL | any change to server-side mutations, domain logic, or concurrency-sensitive code |

CI runs the same suites as `Static checks`, `Unit tests` and `Integration tests` on every pull
request and every push to `main` or a `v*` tag.

## Unit tests

Unit tests must not import Prisma or any server infrastructure — pure logic only.

## Integration tests

- They live in `tests/integration/`, use `node:test` (not `@playwright/test`), and run against the
  isolated PostgreSQL service in `docker-compose.e2e.yml` — never the development database.
- `pnpm test:integration` starts that container (port 5433, data on tmpfs), applies pending
  migrations, and runs the tests. It does **not** reset or re-seed the database.
- `tests/integration/tsconfig.json` with its `server-only` shim is required — do not remove it.
- Add or update integration coverage when changing inventory mutations, concurrency-sensitive logic,
  or other server-side domain rules.
- **One database for every worktree.** The compose file publishes host port 5433 and names no
  project, so each worktree would start its own container on the same port: two sessions cannot run
  integration tests at the same time. If the port is taken, another session is probably using it —
  report it rather than stopping someone else's container, and stop the one you started when your
  task is merged.

## Migrations

Database schema changes are product decisions. Never run `prisma migrate dev`, `prisma migrate reset`
or `prisma db push` — they touch the user's development database. Generate only the migration SQL:
`pnpm exec prisma migrate dev --create-only --name <name>`. The migration is applied the next time
the user runs the stack. Do not try to fix migration checksum drift by resetting a database.

## End-to-end tests

Browser-level e2e testing is paused, and its scripts are gone from `package.json`. Do not add e2e
test files until the e2e infrastructure is rebuilt (tracked in the backlog, #110 onward).

## Browser verification — only when the user asks

Not part of the definition of done; see `collaboration.md` §8 for the decision and its reason. When
the user has explicitly asked for a browser check:

- start the dev server in webpack mode, for example `pnpm exec next dev --webpack -p 3002` — Turbopack
  has repeatedly produced unstable dev-server failures here;
- stop any server you started before finishing the turn. The user tests through Docker Compose; do not
  leave servers running for him.

## Generated and ignored files

`next-env.d.ts` is generated by Next.js and deliberately ignored, because `next dev` and
`next typegen` rewrite it differently.

## A result that depends on where it runs is a defect

Fixed 2026-09-08, and recorded because the shape recurs: `pnpm lint` used to report **93 errors
locally and zero in CI**, all of them in `site/dist/**` and `site/.astro/**` — the Astro site's build
output, gitignored, and never built by CI. The lint rule was unrunnable as written on any machine
where the site had been built, and CI structurally could not reveal it. `eslint.config.mjs` now
ignores both paths; the site's own sources are still linted. A divergence between your result and
CI's is a defect in the check, not something to work around.
